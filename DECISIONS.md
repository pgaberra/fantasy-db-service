# Decision log

Non-obvious choices in this service, one line each. Format and rules: the monorepo root `DECISIONS.md`.

---

[2026-09-11] fantasy-db-service: an unknown path answers 404 through its own `NoResourceFoundException` handler, copied from bff and espn-service (fantasy-workspace#33) — a shared advice library was rejected because the services deploy separately and it would couple their releases for about ten lines, and a catch-all that passes every Spring `ErrorResponse` 4xx through quietly was left for a separate decision across all four services rather than widening this fix.
[2026-09-11] fantasy-db-service: a premium grant truncates its instants to microseconds in the entity, so it holds exactly what `TIMESTAMPTZ` stores (Postgres and H2 both round half up, so an instant ending in ≥500 ns was stored after itself) — rejected: an injected `Clock` ticking in microseconds, which covers only the instants the service stamps and not a caller's `expiresAt`; and changing every entity, since grants are the only rows queried against a freshly stamped `now`.
[2026-09-11] fantasy-db-service: an event about a different subscription takes over a user's one subscription row only if the stored one has ended, or is live but grants no premium while the new one does; two live ones at once log ERROR — the row used to follow whichever event came last, so canceling one of two subscriptions took premium from a user still paying for the other; a row per subscription was rejected because every reader (entitlements, the portal, the admin list) wants the one subscription that counts, and keeping one row keeps that answer in one place.
[2026-09-11] fantasy-db-service: a user's open checkout is stored in its own `pending_checkouts` table, one row per user, replaced only by compare-and-set on the reference the caller read — so two tabs opening checkout at once end up on the same provider transaction, which can be paid once; a row on `subscriptions` was rejected because a checkout is not a subscription until it is paid, and keying the reuse on the Paddle customer was rejected because accounts with an unverified email have none.
[2026-09-11] fantasy-db-service: local `docker-compose.yml` runs `postgres:16-alpine`, the major the staging and production Coolify resources run (checked 2026-09-11), instead of 17 (#113) — local Postgres is only worth having if it matches the servers, since tests run on H2 and a migration is first exercised on the staging deploy; upgrading the servers to 17 was left as Alexander's call rather than decided in a docs fix.
[2026-09-13] fantasy-db-service: the player id remap removes an uncovered row whose old id is another player's destination in the crosswalk, and refuses an apply over such a draft pick (fantasy-workspace#52: Yahoo's 5738 Frk would have sat under ESPN's 5738 Dumoulin in all 7 prod projections) — keeping it broke the "invisible and recoverable" premise the keep-never-drop rule rests on; moving leftovers to negative ids was rejected because every save path would then have to accept ids no pool has, and a collision with an ESPN id outside the crosswalk is not caught here since this service never sees the pool (checked by hand for prod: none).
